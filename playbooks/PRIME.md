# Prime a self-hosted installation

Start here once the dashboard is reachable, the database is migrated, and the API readiness check succeeds. Use the explicit deployment name, configuration path and API origin from [SELF_HOST.md](./SELF_HOST.md).

Read the current workspace, model selection, and runner state before writing. If an outcome is uncertain, read the resource back by provider, workspace or runner host ID before retrying.

## Where the keys come from

The deployment owner supplies issuer credentials from the provider console and generates keys for local services.

agentsfleet issues the CLI session, tenant API keys and runner tokens after the daemon starts. Give the agent secret references or configured files. Record identifiers and status in the handoff.

| Input | Where it originates | Where it goes |
| --- | --- | --- |
| Clerk publishable key, backend secret, issuer | The Clerk project configured for this deployment | The publishable key goes to the dashboard. The backend key goes to the dashboard and daemon. The issuer and API audience go to the daemon. |
| Clerk signing secret | The Clerk webhook endpoint configured for the API | `CLERK_WEBHOOK_SECRET` in the daemon's deployment configuration |
| Database passwords, NATS password | Independent random values generated by the database or deployment operator | The migration and API logins each get their own password. All three NATS nodes and the daemon use the bus credential. |
| Data encryption key, device-code pepper | Independent random values generated by the deployment operator | `ENCRYPTION_MASTER_KEY` encrypts stored secret data. Retain it with recovery material. `AUTH_SESSION_CODE_PEPPER` protects device-code digests. |
| Public HTTPS and runner TLS | The public HTTPS proxy and the private CA used by the operator | The daemon holds the runner leaf and its key. The runner gets the CA certificate. The CA signing key stays with the CA. |
| Inference credential | The provider account, such as a Fireworks API key issued by Fireworks | A secret named for that provider in the operator workspace. The default model record points to that workspace. |
| TypeSafe decision credential | The TypeSafe account, when the runner policy uses a setup decision model | The `typesafe` workspace secret with the `api_key` field. The runner's assigned policy references the catalogue decision model ID. |
| CLI machine session and tenant API key | Browser sign-in issues a CLI credential. An optional key from `agentsfleet api-keys create` inherits its creator's current grants. | The CLI stores the session. Put automation keys in the automation's credential store. Interactive priming works with the operator's CLI session. |
| Runner token | The daemon issues a distinct token during registration | The named runner's private service environment. Save it to the operator's credential store at issuance. |
| Optional provider credentials | The selected providers' consoles | The corresponding [platform secret bags](./operations/admin_bootstrap/001_playbook.md#sync-a-provider-secret-bag) in the platform admin workspace |

The hosted environments use separate 1Password vaults `ZMB_CD_DEV` and `ZMB_CD_PROD`. Their `agentsfleet-admin` item holds the workspace ID and hosted sync key. Provider items hold their own values and are resolved only when needed.

A self-hosted operator can use 1Password or an equivalent product that delivers concealed values via files or stdin. The vault administrator grants `op` access. [Hosted account and vault setup](./founding/01_bootstrap/001_playbook.md) · [Hosted admin bootstrap](./operations/admin_bootstrap/001_playbook.md)

## Establish the operator identity

1. Create the operator account through the configured dashboard and verify the email. Check the signed `user.created` delivery and its Clerk metadata writeback. On a fresh database with an existing Clerk user, replay that delivery before signing in.
2. Add `runner:register runner:write stream:read model:admin platform-key:admin workspace:any` to this operator's Clerk public metadata scopes, preserving the existing scopes and tenant ID. Use a fresh sign-in after changing the grant. [Platform scopes and signup](../docs/AUTH.md)
3. Use an interactive terminal. Set `AF_API_ORIGIN` and `AF_DASHBOARD_ORIGIN` from the installation record. Resolve the workspace UUID and use that workspace.

   ```bash
   export AGENTSFLEET_API_URL="$AF_API_ORIGIN" AGENTSFLEET_DASHBOARD_URL="$AF_DASHBOARD_ORIGIN"
   ```

   The export is silent on success.

4. Run `agentsfleet login` and authorize the terminal in the configured dashboard. Run `agentsfleet whoami` and verify the person, API origin and effective scopes.
5. Run `agentsfleet workspace list` and record the administrator workspace ID as `AF_ADMIN_WORKSPACE_ID`. Run `agentsfleet workspace use "$AF_ADMIN_WORKSPACE_ID"` to select it.
6. Save that workspace ID as `PLATFORM_ADMIN_WORKSPACE_ID` in the deployment configuration. Recreate the daemon with `af_compose up -d daemon` and check readiness again. The tenant ID and Clerk user ID identify different records.

**Evidence** A successful webhook receipt, intended identity, effective scopes, selected workspace ID and readiness after setting the platform workspace.

## Seed the model catalogue

Use the same checkout and Compose project as the installation. The seeder opens the migration-role database and diffs it against the pinned catalogue. Install the root Bun dependencies first.

1. Run `af_compose run --rm catalogue`. Read the identities, changes and prices in the diff.
2. Run `af_compose run --rm catalogue --apply` after reviewing the diff. Expect the apply to exit zero.
3. Run `agentsfleet platform models list --json`. Verify the required model and its price.

Apply the diff once reviewed for this deployment. The seeder updates model identities and prices in one transaction and removes catalogue rows absent from the snapshot, except decision rows. An identical apply has no writes.

For catalogue overrides and decision model pricing, use [Model catalogue priming](./operations/model_catalogue/001_playbook.md).

**Evidence** Capture the diff and confirm the intended setup model, context and price are in the applied catalogue.

## Configure inference

Choose a provider and catalogue model with tool support. Set `AF_PROVIDER` to the provider ID and `AF_MODEL` to its exact model identifier. Check `agentsfleet secrets show "$AF_PROVIDER"` and `agentsfleet platform models default list --json`.

If the named secret is missing, stream its value into the selected operator workspace. This example reads an operator-provided 1Password reference.

```bash
set -o pipefail
op read "$AF_PROVIDER_REF" |
  jq -Rse --arg provider "$AF_PROVIDER" --arg model "$AF_MODEL" '
    rtrimstr("\n") |
    if length == 0 then error("empty provider credential")
    else {provider: $provider, model: $model, api_key: .}
    end
  ' |
  agentsfleet secrets create "$AF_PROVIDER" --data=@-

agentsfleet platform models default use \
  --provider "$AF_PROVIDER" --workspace "$AF_ADMIN_WORKSPACE_ID" --model "$AF_MODEL"
agentsfleet platform models default list
```

For an existing valid secret, select the default directly. When rotating a credential, use the same JSON form with `secrets update` to replace the value under its existing name. For an approved custom HTTPS endpoint, include its `base_url` in the secret and pass `--base-url` when selecting the default.

When the runner uses a setup decision model, create the `typesafe` secret with the account's `api_key`. Seed the decision model using approved pricing. Record the model's ID for the runner policy.

[Decision model seeding](./operations/model_catalogue/001_playbook.md#seed-the-decision-model)

Fix the secret or catalogue before retrying a failed model selection.

**Evidence** The list shows the selected default, and the admin workspace shows the named secret. The first setup and runtime replies prove the key works. For a decision model, also prove an edit that uses it.

[First fleet verification](./SELF_HOST.md#5-prove-the-first-fleet)

## Enroll a runner

1. On the Debian 13 runner, install `bubblewrap nftables iproute2 ca-certificates git openssl curl jq`. Prepare cgroup v2 with the `cpu`, `io`, `memory` and `pids` controllers, EROFS, user namespaces and the networking required by the selected policy.

   Verify the runner archive digest against the trusted release's `candidate.json`. Separately verify the signed toolbox manifest and its image digest. Put the runner at `/usr/local/bin/agentsfleet-runner` and run `agentsfleet-runner probe` on that host.
2. Check `agentsfleet platform runners list --json` for the host's stable private DNS name. If absent, register it. Set `AF_RUNNER_POLICY` to the path of the reviewed runner policy JSON file.

   Set `AF_RUNNER_TOKEN_FILE` to a new path in a private directory.

   The policy includes the allowed network, sandbox tier, worker count, durable-task setting, registry allowlist and extra binds. Use the catalogue decision model ID when the setup decision policy is enabled. [Runner policy example](./operations/runner_onboarding/001_playbook.md#steps) · [Policy wire schema](../cli/src/commands/platform/runner-schema.ts)

   ```bash
   agentsfleet platform runners register --host-id "$AF_RUNNER_HOST" \
     --policy "$AF_RUNNER_POLICY" --token-out "$AF_RUNNER_TOKEN_FILE"
   ```

3. Put the runner's HTTPS API origin, private stream origin `https://<private-runner-dns>:4443`, TLS CA path, and issued token in `/etc/default/agentsfleet-runner` with mode `0600`. Use the environment field names documented in the [runner service](../deploy/baremetal/agentsfleet-runner.service). Install the [runner configuration](../deploy/baremetal/agentsfleet-runner.toml) at `/etc/agentsfleet/agentsfleet-runner.toml`.

   Staging the verified toolbox replaces the existing staged toolbox set.

   ```bash
   sudo bash -c 'source deploy/baremetal/toolbox.sh; install_toolbox "$1" /var/lib/agentsfleet-runner/toolbox/incoming' bash "$AF_TOOLBOX_DIR"
   ```

   Verify that the image, manifest and signature are present in the incoming directory.
4. Install `deploy/baremetal/agentsfleet-runner.service` under `/etc/systemd/system/` with mode `0644`. Run `sudo systemctl daemon-reload` and expect silent success. Run `sudo systemctl enable --now agentsfleet-runner` and check that the unit starts.
5. Check `agentsfleet platform runners show "$AF_RUNNER_ID"`. It should report `online`, a fresh heartbeat, and the assigned engine and policy. Request `agentsfleet platform runners self-test "$AF_RUNNER_ID"` and read the result with `show`.

   If an existing registration's token is lost, use `platform runners rotate-token` with a fresh output path. Keep the registration ID.

**Evidence** Runner ID, verified host probe, assigned policy, online heartbeat, and passed self-test.

## Finish and hand off

For each additional capability selected in the install record, configure its own credential bag and run the [operations verifier](./operations/README.md#optional-capabilities). Restart the daemon after changing any startup-read bag. Record the result for each enabled capability.

Return to [first fleet verification](./SELF_HOST.md#5-prove-the-first-fleet). The handoff records the deployment revision, workspace, provider, catalogue model, runner, draft, fleet and turn IDs.

Keep non-secret evidence for the completed and skipped checks. Use [recovery](./operations/recovery/README.md) for a restored database, upgrades and key rotation.
