## Problem Statement

Two problems were tangled together for most of the session. They are independent,
and separating them is the main result of this document.

**Problem 1 — nobody knows whether a diagnosis is worth anything.** The product
has no user and no demand evidence. `library/*` holds three AI teammates that
chain (responder diagnoses, repairer proposes a bounded fix as a draft Pull
Request behind a human approval card, verifier proves the signal cleared). None
has ever produced a diagnosis anyone read.

**Problem 2 — no fleet declaring a *mintable* credential can run.** When policy
assembly finds a declared mintable credential without an approved grant,
`deliver.rs:62-70` parks the delivery and writes nothing. The stream entry is
never acknowledged, so it redelivers every second forever, while the dashboard
reports `ACTIVE`. The grant it waits for cannot be created: every
`INSERT INTO core.integration_grants` in the repository is in a test file, the
tenant API exposes only list and revoke, and `KIND_INTEGRATION_GRANT` is written
by nobody.

**They do not block each other**, and the first draft of this document wrongly
claimed they did.

## The fork the first draft missed

`Assembled::Ungranted` is produced only by `first_ungranted`, which iterates
`declared.mintable()` (`afd_gate/src/policy/grants.rs:61-69`). A credential is
mintable only when its stored handle names a connector with `Supply::OnDemand`
(`afd_credential/src/secrets/connector.rs:301-308`). The registry is `static,
github, zoho, jira, linear`, and its own comment says why the rest are absent:

> *"The api-key connectors — datadog, grafana, fly — are deliberately absent:
> their key is used directly and never reaches a broker, so a row for them would
> be a row nothing dispatches on."* — `connector.rs:215-219`

**Consequence: a responder declaring no mintable credential never produces `Ungranted`**, because `declared.mintable()` is empty. `first_ungranted` still runs; it iterates an empty slice.
The only credential in the existing responder's five that parks is `github` —
which is exactly why the observed daemon log read `github needs a grant for
github`. One clause matters: `jira` IS in `DECLARED` with `Exchange::OAuthRefresh` → `Supply::OnDemand`. It escapes minting only because `TRIGGER.md` stores it as `{host, basic_auth}` with no `integration` field, so `mintable()` short-circuits at `.get(FIELD_INTEGRATION)?`. **The mechanism is the stored handle, not the declared name** — a jira secret re-stored with an `integration` key would park too.

This is good news, not a setback. The evaluation can happen now, with zero
security-boundary work.

## Status Quo

Chosen over three alternatives: **triage burns the on-call hour.** The alert
fires and a human spends forty minutes in Grafana assembling what happened
before touching a fix.

Today is the worked example. A delivery stalled at 02:43 PM; finding out why took
a human walking the dashboard, then reading daemon logs, then reading source —
and the decisive line (`reason="github needs a grant for github"`, 8 occurrences
against 789 of `"no leasable work"`) sat in a log nobody watched.

## Target User & Narrowest Wedge

**The user:** the founder, on agentsfleet's own on-call. Chosen over "a specific
person I can name" — there isn't one. Dogfooding risk (an unusually forgiving
user of their own product) is accepted for the tightest available feedback loop.

**The wedge:** a new `runner-triage` responder bundle that reads
`GET /v1/fleets/runners/{runner_id}/leases` — outcome and failure cause joined in
one round trip — and writes one diagnosis. It declares one `static` credential
(an agentsfleet API token). `static` maps to `Exchange::Stored` → `Supply::Inline`
(`connector.rs:86-89`), so it is **not mintable**: no grant, no approval card, no
security-boundary work.

## Constraints

- Pre-product, zero users, never deployed to production (`agentsfleetd-prod`
  reads `pending`).
- **The lease history has its own endpoint, and it is the right input.**
  `GET /v1/fleets/runners/{runner_id}/leases` (`afd_api_operator/src/handler/operator/leases.rs:18`,
  published in `public/openapi.json`): *"Each lease is joined to its Fleet event,
  so outcome and failure cause arrive in one round trip."* The first two drafts
  wrongly claimed no such API existed. The real constraint is narrower: it is an
  operator-plane read requiring `RUNNER_READ`, so the wedge needs an agentsfleet
  API token, a self-referential network-allowlist entry for the API host, and that
  scope.
- **agentsfleet's telemetry reaches Grafana Cloud only** — all three collector
  pipelines terminate at `otlphttp/grafana` (`deploy/fly/otelcol-dev/config.yml:66, 92-104`;
  prod corroborates). Elastic receives none of it. This matters less now: the
  wedge reads the lease API, not Grafana.
- **The counters and the lease table were never meant to reconcile.** The same
  endpoint description explains the 139: lifetime totals *"count transitions as
  they happen, not surviving rows"*, and settled leases are swept after 30 days.
- The daemon owns no timer. A cron schedule is stored intent mirrored to QStash,
  which posts back to `/v1/ingress/qstash/schedules` (`afd_cron/src/lib.rs:4-11`).
- `Vault::declared` ends the event when a declared name has no stored secret
  (`afd_credential/src/secrets/mod.rs:120-146`).
- The three `library/*` teammates are in the repo and not offered by the
  dashboard's Install-fleet page, which listed only `github-pr-reviewer`
  (live-dashboard observation, app-dev, 2026-09-08 — the catalogue is API-served,
  so this is not checkable from the repository).

## Premises

1. **The wedge is the responder alone.** Repairer and verifier are the story, not
   the first ship.
2. **The founder's own system is a legitimate first workload** — 222 failed
   leases supply material. Material, explicitly not demand.
3. **~~Nothing ships until the grant write exists.~~ REVISED:** the grant write
   blocks every teammate declaring a *mintable* credential (github, zoho, jira,
   linear). It does not block a wedge whose only credential is `static`. Verified above.
4. **Execution is already ephemeral** — one lease per event, sandbox dies. What
   persists is the subscription and the incident memory. *(Reworded after Codex
   challenged the original phrasing, which conflated durable memory with a
   long-lived agent object.)*
5. **The comparison set is AI-SRE** — Datadog Bits AI, Resolve AI, Traversal,
   incident.io — not code review.
6. **Three teammates is too much surface for zero users.** The repairer pushes
   code and must not be first.

## Approaches Considered

### Approach A: Unblock the platform, then dogfood
Grant path for all five credentials, demo hosts repointed, responder runs as
designed. Effort M, risk Med. **Not chosen** — five credentials of security
surface before knowing whether a diagnosis is worth reading.

### Approach B: Readiness contract first
Fleets stop reporting `ACTIVE` when they cannot fire and name what is missing.
Effort L, risk Low-Med. Kills the class — which has bitten twice in two days
(prior learning: `configured:true` proves a secret's name exists, not that it
opens). **Right trajectory, wrong order** — infrastructure for an unvalidated
product.

### Approach C: runner-triage responder over the lease API — CHOSEN
A new bundle declaring one `static` credential. No grant, no approval card, no
auth-boundary diff. Round 1 scoped this to Grafana; round 2 found the lease
endpoint, which carries outcome and failure cause already joined and removes the
open question of whether Grafana holds the signal at all. Effort S.

### Approach D: Create grants at install time
Insert pending grant rows from the bundle's declared mintable credentials when a
fleet is installed. The vocabulary already exists — the reason string **"Declared by the fleet
bundle at install"** appears at `afd_wire/src/grant.rs:124` and
`afd_approval/tests/integration_grants.rs:41`. **Both are test-only**
(`mod tests` opens at `grant.rs:87`), which is the same evidence class this
document rejects for the grant INSERTs. D rests on naming precedent, not on an
existing production writer. The second draft called it production code; that was
wrong. **Not chosen for the wedge** (the wedge needs no grant at all)
but this is almost certainly the right shape for Problem 2, and a better one than
the first draft's lazy-on-park: it avoids the lease hot path, avoids adding a
second writer across `afd_approval`'s stated ownership boundary
(`afd_approval/src/grant.rs:20-23`), and matches the vocabulary already in the
wire types.

## Recommended Approach

**C for the wedge. D for Problem 2, as separate work.**

What ships in the wedge — three code items, no security-boundary write:

1. **A new `runner-triage` bundle** (`SKILL.md` + `TRIGGER.md`). Not a trimmed
   config: the existing responder's instrument set is ES|QL over `logs-*` and
   `traces-*`, none of which queries runner leases. Declares one `static`
   credential, one cron trigger, `http_request`, `memory_store`, `memory_recall`,
   the API host on the network allowlist, no `repositories`, no
   `repository_access`.
2. **One diagnosis, with a real destination.** Fields: affected runs, evidence
   links, likely cause, stated uncertainty, next step — *format deferred to the
   Assignment's hand-written artifact, deliberately.* It lands in
   **`EventDetail.response_text`**, written at `afd_fleet/src/lease/finalize.rs:85,94`
   and read at `GET /v1/workspaces/{ws}/fleets/{id}/events/{event_id}`, rendered in
   the fleet thread. Round 1 said "the fleet event tail" — wrong: the tail is
   read-only and `EventSummary` carries no `response_text`, so the diagnosis is
   reachable via the detail read, not the listing.
3. **Incident memory — prompt-level, no code.** `memory_store` / `memory_recall`
   already exist (`tool_bridge_registry.zig:24-25`), and
   `schema/820_memory_entries.sql` is present. Dedupe rule, stated concretely:
   fingerprint = failure class + error-message hash + fleet id; re-escalate only
   on a new class, or a count crossing a threshold.

Explicitly skipped: repairer, verifier, repository writes, every mintable
credential, the readiness contract, deny-side event termination, broad onboarding.

## Success Criteria

**Threshold, so the criterion can actually fail:** the responder is useful if it
saves **≥20 minutes on 3 of the next 5 incidents, with zero confidently-wrong
diagnoses.** A wrong diagnosis at 3am is worse than none — it sends the on-call
down the wrong path — so wrong diagnoses are counted separately and one is
disqualifying.

**One gate, one supporting experiment.** The gate is the live one above. The
supporting evidence: replay it over a sample of past lease failures and score the
diagnoses blind. How many of the 222 have a known cause is unmeasured — the one
inspected row shows a bare `Model not found` with no root cause — so size the
sample after looking, and do not assume the answers exist.

Two honest limits: you cannot re-run an incident, so baseline and treatment are
different incidents and not strictly comparable; and the founder authors the
diagnosis format in the Assignment and then grades the tool against their own
template.

**Scoped secondary:** every *ungranted* park raises a card. Not "no delivery ever
parks invisibly" — there are eleven `no_work(...)` call sites in
`rustd/crates/afd_fleet/src/lease/` and the wedge touches none of them. The
general guarantee is Approach B.

## The Assignment

**Take today's outage. Write the diagnosis by hand — the one you wish had been
waiting for you. Then write down how long it took.**

Not "go build the responder." Two things fall out that nothing else gives you:

1. **The baseline number.** You cannot claim the responder saved an hour without
   knowing what the hour was. This is the cheapest way to get one, and it expires
   when today's outage does.
2. **The output format.** Writing it by hand tells you which fields actually
   mattered — what you reached for, what you ignored, what you wished you had.
   Guessing that from an empty page produces a teammate filling in a template
   nobody reads. Item 2 above is deliberately blocked on this artifact.

If the hand-written diagnosis turns out quick and obvious, that is the most
valuable finding available today: the wedge is wrong, and triage is not where
your hour goes.

## Appendix — Problem 2 findings (the grant path, not the wedge)

Verified this session and carried for whoever builds Approach D.

- **Evidence contract, currently undocumented:** `RESOLVE_GATE` matches
  `g.service = r.evidence->>'service'` (`afd_approval/src/sql.rs:98`). A raised
  gate must carry a `service` key spelled exactly as `Connector::name()`. Omit it
  and the gate resolves cleanly while the grant stays `pending` — a failure with
  no error.
- **The approve path's grant arm has never been exercised.** The statement
  exists, but `afd_approval/tests/support/gate_lane.rs:99-102` says
  *"Deliberately NOT `integration_grant`"*. Whoever builds D writes that test.
- **Duplicate-run hazard:** `Inbox::won` lands a continuation event when the
  resolved gate carries an `event_id` (`afd_approval/src/inbox.rs:247-261`).
  Since an ungranted park leaves the original event leasable, a grant gate raised
  *with* an `event_id` would run the work twice. D must state which shape it uses.
- **Denial terminates nothing today.** `RESOLVE_GATE`'s `granted` arm moves only
  the grant row's status; a denied park re-parks every second forever.

Rejected, with evidence: round 1 said the scope-transfer clause names a rule that

Unresolved, carried forward deliberately:

- How many of the 222 past failures have a recoverable cause is unmeasured.
