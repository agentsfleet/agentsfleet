## Overview

**Goal (testable):** the daemon runs its fleet workflow against a real multi-node Dragonfly cluster as its only datastore, and every accepted event survives loss of the in-memory datastore.
**Problem:** the live probe shows the current design cannot run on a cluster at all — the at-most-once append is a two-key Lua script that answers `CROSSSLOT`, readiness and outbound delivery are single hot keys, the hub uses global pub/sub which a cluster broadcasts to every node, and acceptance is queue-only so a lost queue is lost work.
**Solution summary:** move acceptance into PostgreSQL so the queue carries only single-key appends; route every command, script, subscription and scan by slot through one cluster-only `afd_datastore` boundary; shard readiness by fleet hash; prove each change on the local cluster in the integration lane. Redis is retired: there is no standalone transport, no topology selector and no parity matrix. Cloud Swarm proof and live cutover belong to a follow-up spec once the local lane is green.

### §2: Durable admission and stable logical identity

Dependencies: §0.3 and §5. Acceptance means a committed PostgreSQL admission row before any success response. The row carries producer identity (steer request, webhook delivery id, schedule fire, gate continuation, install, outbound answer), the fleet, the payload digest, and a status that a replay dispatcher advances; the queue append is a single-key `XADD` recorded back as a physical receipt. Duplicate producer identity is a unique-index conflict, which replaces every Redis dedup claim; `once.rs` and its two-key script are deleted, not kept behind a flag. Numeric event ids and the existing stream entry ids stay as the physical receipt; logical identity is the ledger row.
Replay re-appends any admitted row without a receipt after a bounded age, under the same fencing the lease path already enforces; settlement and billing key on the ledger row so a replayed receipt cannot debit twice.

### §3: Retention, memory limits, and backpressure

Dependencies: §2. `MAXLEN ~` trimming is replaced by an `XTRIM MINID` on the acknowledgement path, bounded below by the oldest pending or undelivered entry (an unreceipted admission has no entry to trim); acknowledged history keeps a fixed bound of 1,000 entries on fleet and outbound streams alike. ### §7: Restart and cutover safety

Dependencies: §2–§5, and this section's fixes land BEFORE §6's final acceptance run — §6 grades the lane, and three of the dimensions it grades are reopened here, so grading first would grade a known-broken guarantee. Within the section, 7.3 precedes 7.2 (a runner retrying into a settlement guard that rejects repeats gains nothing) and 7.6's durable obligation is designed alongside 7.3, so committing the result does not open a second gap between result and delivery. The cutover is a fresh start: PostgreSQL is rebuilt and Dragonfly provisioned empty, and every pre-cutover event is discarded by decision (Discovery). Nothing is imported, so there is no import tool, no receipt and no boot gate for one. What must hold instead is that work accepted AFTER cutover survives every ordinary restart and deployment: PostgreSQL is authoritative for what was accepted, what completed and what delivery is still owed; Dragonfly accelerates discovery and delivery and losing its contents erases no obligation; a deployment replaces processes and neither datastore; a retry reuses the operation's identity, because a timeout does not prove an operation failed. The dimensions below are the failures an adversarial read of §2–§5 found the current code has (Discovery, 2026-09-14).

- **Dimension 7.1**: the readiness index gains a PostgreSQL-driven writer. Today it has two — ingress marks a fleet as it admits, and the reclaim sweeper re-marks one when the STREAM says it still holds work — so a fleet whose lease expired while its stream was lost is marked by neither, no runner polls it, and `reclaim_prior_active` never fires, because it only runs when a claim wins that fleet. The reclaim sweeper therefore also asks the ledger, on its existing interval and behind its existing batch bound: which fleets hold an `active` lease past `lease_expires_at`? The answer is a readiness mark ONLY — the sweeper never flips the lease, because `reclaim_prior_active` (`afd_fleet::lease::assign::try_candidate`) re-leases from PostgreSQL alone, before the stream is read, and requires the lease still `active`; a flipped lease is invisible to the one path that recovers it. Discovery reads PostgreSQL in the sweeper and never on the empty-poll path, whose zero-PostgreSQL property is deliberate. The wrapping cursor is exercised at `BATCH_LIMIT + 1` fleets, never at a literal a constant can drift past. The datastore probe runs with no row lock held and each void is a compare-and-set pinning the receipt it probed. ## Invariants

1. Admitted work has a committed ledger row before success; crash-boundary tests enforce it.
2. Replay cannot duplicate settlement or billing; ledger uniqueness and lease fencing enforce it, with no exactly-once promise for external side effects.
3. No trim or cleanup removes the only recoverable copy of unfinished work.
4. Every multi-key operation shares a slot by construction or does not exist; the cluster suite refuses a new one.
5. A seed that is not a cluster refuses boot; nothing falls back to a standalone path or an empty queue.
6. Every suite passes against the local cluster in one lane; missing provenance fails the grader.
7. Owned local datastores alone receive resets and fault injection; shared endpoints are refused before mutation.
