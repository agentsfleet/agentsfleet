## Overview

**Goal (testable):** A decision reservation runs at most 22 statements and holds no lock across a round trip, a Stop that commits while a run is being issued leaves no run or names and cancels it, an effect item insert never waits on a renewal, an idle setup page reads Postgres once per 15 s, the runner sends no ping and runs one clock, whose round sends the heartbeat and the renewal batch, and a lost wake is reproducible on demand.

**Problem:** Four reviews traced the flows and every clock in source. The counts are call sites read, not measurements.

- **Stop can miss a run.** The API answers "cancelled" while the run works and bills until its first renewal. Two interleavings, both in §3.
- **Decision reservations queue on one lock.** A reservation runs 51 statements, 21 of them locking (`afd_fleet/src/durable_task/decision/allocate.rs`). It holds the fleet's thread lock across about 27 of them, funds in three more transactions, then takes every lock again to issue. Before `9caf88c7c`, 100 identical reservations failed the coverage build in Continuous Integration (CI) with `PoolCapacity { role: "api", waited: 5s }` (that commit's message). The commit shortened the queue and left the first lock. Production runs five connections per replica (`deploy/fly/agentsfleetd-prod/agentsfleetd.toml`, `[database.api] max_connections`).
- **A failed funding is never released.** Its call stays `reserved` and counts against the fleet budget, the run's credit and profile changes for good.
- **Writers lock more than they write.** Renewals, reports and heartbeats take `FOR UPDATE` on rows whose keys they never change, so a child insert that references the row waits behind them.
- **The setup page polls.** It re-reads Postgres every second per open page, four reads each time (`afd_api_tenant/src/handler/draft/stream/body.rs`, `QUIET`).
- **The runner ticks three clocks.** A 5 s renewal and a 15 s ping run beside the 10 s heartbeat (`afr_supervisor/src/uplink/renewals/mod.rs`, `afr_supervisor/src/downlink/io.rs`).

**Solution summary:** The reservation becomes reads with no lock, then one issue statement that locks its rows for that statement only and is also the issuance. Stop holds the thread first, and the issue re-checks its turn after it waits. Row locks drop to the weakest mode that still excludes other writers. The setup page reads on a bus notice or its 15 s heartbeat. The runner sends no ping, and its renewal round rides the heartbeat's clock. Before any of it changes a table, Indy rules on whether setup, chat and durable tasks converge on threads, turns, runs and items (§1).

**Design flow:**

```
reserve   today  peek ─► locks on workspace, fleet, thread, run, task, source turn, call, held for 27 statements
                 ─► commit `reserved` ─► funding in 3 more transactions ─► every lock again ─► `issued`
          after  peek ─► 16 statements, no lock held between them ─► ONE issue statement:
                 fleet KEY SHARE ─► thread, run, task, source turn FOR SHARE ─► clock ─► INSERT call + payload
                 inserted: issued, key leaves  ·  conflict: the saved call, replayed  ·  no row: stale state
Stop      today  one statement; waits on the thread inside it; snapshot predates the run insert
          after  hold thread ─► stop_turn.sql        issue: turn read FOR SHARE, re-checked after its wait
setup     today  observe every 1 s      after  observe on a `Changed` notice or a bus gap; the heartbeat reads nothing
runner    today  renewal tick 5 s · ping 15 s · heartbeat 10 s
          after  one clock: a 10 s round sends the heartbeat and the renewal batch · run expiry 38 s
```

### §2 — A decision reservation is reads, then one issue statement that is also the issuance

Traced at `9caf88c7c`. Paths in this Section are under `afd_fleet/src/durable_task/`. A *call* is a row of `runner.decision_calls`. Its private request is a row of `runner.decision_payloads`, and dispatch refuses a call that has none. A fleet has one thread row and at most one live run.

**Today.** `decision/allocate.rs:35-47` compares the presented fence, then reads the call by run and operation with no lock; a hit answers `existing`. Otherwise `allocate.rs:78-145` opens a transaction and holds, to its commit, the workspace and fleet key-share lock, the thread `FOR NO KEY UPDATE` and the run `FOR UPDATE` (`guard.rs:78-120`), the task `FOR UPDATE` (`decision/ownership.rs:117-124`), the source turn `FOR UPDATE` (`sql/lock_source.sql`) and the call. Under them it checks the profile switch, prepares the request, resolves a retry, looks the assessment up, checks the budget and inserts the call as `reserved` with its payload (`decision/intent.rs:32-36`). `decision/fund.rs` then funds with no lock. `decision/dispatch.rs:57-99` takes every lock again, re-proves authority (`decision/verify.rs`) and flips the call to `issued` (`decision/sql/issue.sql`).

**Mechanism.**
- *State authority:* `runner.decision_calls` and its five unique keys. A call row exists only as `issued`: the insert is the issuance, and `issued_at` is never NULL. The column, its check constraint and the readers of `Call::issued` stay, because `find_call.sql` serves the receipt path too.
- *Guarded transition:* the issue statement inserts the call and its payload only when its predicates hold on rows it has locked for that one statement.
- *Commit before release:* the issue statement autocommits. The provider key leaves in the response only after the issue statement returned an inserted row.
- *Failure assumptions:* one Postgres primary at READ COMMITTED. A row lock makes the statement re-read that row's latest committed version after a wait; a row the statement only joins is read as of the statement's start. A daemon that dies after the issue statement leaves an issued call whose replay answers `existing`.

**The statements.** A reservation with a Message assessment, no named task, no retry and the run's own turn as its source runs these 18, none in a transaction with another; the two `find_call` reads keep the one-statement transaction `fetch.rs:33` gives each read. The reads hold one pooled connection at a time and none across the wallet read, which takes its own as `decision/fund.rs:98` does today.

### §3 — Stop takes the thread first, and the issue re-checks its turn after it waits

Three interleavings let a Stop miss a run or fail. All close without removing a lock. `thread.runs.cancel_requested_at` stays: fleet archive uses it to end runs without settling a turn.

**Stop waited inside its own statement.** `History::stop` (`afd_turns/src/view/history/mod.rs:150-168`) opens a transaction and runs `stop_turn.sql`, whose first step locks the thread inside the statement (`afd_turns/src/view/stop/stop_turn.sql:20-24`). While an issue holds the thread, Stop's snapshot predates the run insert and Stop marks no run. The draft Stop avoids this with a hold statement of its own (`afd_setup/src/message/stop.rs:33-42`, `afd_setup/src/sql/message/hold_thread.sql`). The fleet Stop does the same: `History::stop` runs a new `afd_turns/src/view/stop/hold_thread.sql`, the fleet `FOR KEY SHARE` and then the thread `FOR NO KEY UPDATE`, then `stop_on`, in its one transaction. The fleet comes first, as in the issue statement and the report, so a fleet delete, which holds the fleet `FOR UPDATE` and cascades to gates and threads, excludes Stop instead of meeting it at a gate. `stop_turn.sql`'s own thread step stays and finds the lock held. The order stays thread, then turn, then run.

**Stop landed between the assignment and the run insert.** The issue (`afd_fleet/src/run/issue.rs:104-166`) takes the host row in a statement of its own, then runs `insert_run_with_turn.sql`. That statement's only lock wait is its `held` step's update of the thread (`:24-32`), and its turn join (`:49`) is a plain read with no settled or fence test. A Stop that committed before the insert is therefore ignored (Dimension 3.1). A Stop that commits while `held` waits on the thread is on neither the statement's snapshot nor a lock (Dimension 3.2). The join becomes a locking read: `FOR SHARE OF` the turn, with `settled_at IS NULL AND run_fence = $fence` on that row. `FOR SHARE` conflicts with Stop's update, so Postgres re-reads the row after the wait and re-checks both predicates. `FOR KEY SHARE` does not conflict and re-checks nothing. A refused issue returns no row, and the pass logs `run_assignment_lost` as it does for a lapsed assignment (`afd_fleet/src/run/pull/step.rs:62-87`); that stays.

Measured at build on Postgres 19.0, the lane's `postgres:19-alpine`, in the production statement. The issue holds the host and then the thread, so a Stop that holds the thread first has committed by the time the issue reads its head. Any locking read then follows the committed version and re-checks both predicates, and a plain read keeps the statement's snapshot: Dimension 3.2 is red with the locking clause removed and green with `FOR KEY SHARE`. `FOR SHARE` stays because it also waits for a turn update still in flight, which `FOR KEY SHARE` reads past. The test issues as delivery does, `issue_for_revision` under the head's proof: without a proof, `durable_task/sql/issue_source.sql` reads the turn again with `settled_at IS NULL` and already refuses, so Dimensions 3.1 and 3.2 were green on the parent through `runs.issue`. The Dimensions of §2 and §3 that wait on a lock rerun when the Postgres major version changes (SPEC-PIN).

**A fold retry against Stop.** `assign_inputs.sql` rewrites, on a retry, the folded turns a run already holds. It takes no thread lock and runs outside a transaction (`afd_fleet/src/run/fold.rs:118-134`). Stop holds its target and then updates every turn the run serves (`stop_turn.sql:49-62`), so the two can take two folds in opposite orders and deadlock, on the parent commit too. The fold statement's `run` step takes the thread `FOR NO KEY UPDATE`, which puts it behind Stop. Approval resolution has the same shape against Stop (D3: Indy picked "Fix here"). `resolve_gate.sql` updates the gate and then the fleet's unsettled turns (`afd_approval/src/sql/resolve_gate.sql:2,29`), and Stop locks the turn and then closes its gate (`stop_turn.sql:30,63`). The resolution gains two first steps, in the order the issue statement of §2 takes them. The first reads the gate's fleet with no lock, within the caller's scope when one is given, and takes that fleet `FOR KEY SHARE`; the second takes its thread `FOR NO KEY UPDATE`; the update of the gate reads from them. The fleet comes first because fleet delete holds the fleet `FOR UPDATE`, closes the setup-card gates and then cascades to the thread (`afd_setup/src/creation/delete.rs:32-39`, `afd_approval/src/grant_sql/cancel_setup_cards.sql`): a resolution holding the thread and waiting on a gate would deadlock with it. The action id is not unique, so the steps select by the set of fleets its gates name. It stays one autocommit statement (`afd_approval/src/inbox/resolve/mod.rs:125`). Its writes are `UPDATE` targets, so after a wait Postgres re-checks `resolved_at IS NULL` and `settled_at IS NULL` on the rows Stop wrote.

### §6 — The runner runs one clock, and the renewal round rides it

**Ping.** The runner stops sending it (`afr_supervisor/src/downlink/io.rs:100-110`, spawned at `downlink/mod.rs:243`), and the `Ping` command in `client/stream.rs` stays only under `cfg(test)`, where the telemetry tests use it as their request. The daemon keeps answering one, so the protocol version stays `agentsfleet.runner.v4` and no deploy order exists; removing the frame is a later protocol revision. The daemon never counted a ping as liveness, and any unanswered request already ends the session (`afr_supervisor/src/uplink/mod.rs:106-117`). With no ping, the heartbeat is the only traffic on an idle session, and the transport closes an idle session at 30 s with no keep-alive (two literals in `af_stream/src/h3/trust.rs`). The 30 s becomes `STREAM_IDLE_TIMEOUT` in `af_core/src/timing/mod.rs`, which `af_stream` reads.

**One round clock** (D2: Indy picked "Ride the heartbeat"). Today the heartbeat loop sleeps its interval after each answer (`afr_supervisor/src/downlink/policy/mod.rs:118-178`) and the renewal loop ticks beside it (`uplink/renewals/mod.rs:123-161`, started at `downlink/mod.rs:91-97`). After, one sleep is left. The renewal loop keeps it, in the connection task, because that task outlives the heartbeat: at shutdown the heartbeat stops and runs in flight keep `SHUTDOWN_GRACE`, 35 s (`afr_supervisor/src/shutdown.rs:6`, `halt/mod.rs:3-9`), longer than the runner keeps an unrenewed run. A round is due one heartbeat interval after the previous round was sent, or when that round's answers are in, whichever is later, so a daemon slower than the interval is never sent rounds back to back. The interval is the one the daemon advertises (`HeartbeatResponse.heartbeat_interval_ms`), floored at 1 s as today. `Heartbeat::apply` writes it to a watch on the stream handle, which holds `HEARTBEAT_INTERVAL` until a beat answers. At its due instant a round sends the renewal batch for the runs held, no frame when none is held, and wakes the heartbeat loop, which beats. The wake is one stored permit on the stream handle: sending it never blocks and needs no receiver, and a wake that lands during a beat in flight or a backoff pause is kept for the loop's next turn. A session with no heartbeat loop, as the test runner has, renews all the same. The frames stay `Up::Heartbeat` and `Up::RenewBatch`: a renewal batch splits at the control frame bound (`uplink/renewals/batches.rs:10-47`) and a heartbeat cannot, so the protocol and both daemon handlers are unchanged.

- **The heartbeat loop** loses its cadence sleep. It beats when a round wakes it, when a hold saturates (as today) and, after a failed beat, on the `backon` pause it already takes. A pushed policy no longer postpones the beat: today the `continue` at `policy/mod.rs:149` restarts the sleep, so each pushed policy moves the next beat a full interval out. A beat a saturated hold sent just before a round is followed by the round's own beat, at the cost of one runner-row write.
- **Reconnect and refusal.** A new connected session runs a round at once, as the renewal loop does today (`renewals/mod.rs:140-148`). A round that failed to send, or in which a run was refused retryably, is followed by a round one `STREAM_ANSWER_TIMEOUT` (5 s) after it was sent, or one interval when that is shorter. Every round wakes the heartbeat, a retry round included: the daemon closes a session with no heartbeat for two intervals (`afd_gateway/src/connection/liveness.rs:33-41`), and a renewal does not move that clock. The daemon refuses a frame retryably when the frame missed that same bound (`afd_gateway/src/connection/dispatch/renewal.rs:36,140-150`).
- **Arithmetic and config.** A round must leave the 5 s answer bound, the 7 s reconnect budget and the 15 s `RENEWAL_WINDOW`, 27 s, strictly inside the run's expiry. At the 10 s heartbeat that is 37 s, so `RUN_TTL` becomes 38 s and both daemon configs move `ttl_seconds` from 35 to 38. `ttl_seconds` is at least `heartbeat_interval_seconds` + 28. `heartbeat_interval_seconds` is at most the least of four bounds: the offline bound it has today, 24 (interval plus answer bound under `STREAM_IDLE_TIMEOUT`), `ttl_seconds` − 28, and (`ttl_seconds` − 1) / 3, which keeps three renewal rounds, the funds-check cadence, inside one run expiry. `FUNDS_CHECK_TICKS` moves to `af_core::timing` so the bound and the daemon's counter read one constant. The daemon counts frames, so the cadence holds for a batch that fits one frame; a batch splits only past 2 MiB of unrecorded usage, as today.

`RENEWAL_TICK`, `STREAM_PING_INTERVAL` and the runner's `renewal_interval_ms` go. Each assert keeps its message's meaning:

## Interfaces

- Runner decision reservation: `existing` with state `reserved` is never answered, and `reserved` leaves the OpenAPI enum. Status codes and error codes are unchanged; a run lost between the reads and the issue statement answers `RUN_NOT_FOUND` or `RUN_STALE_FENCING_TOKEN` as today, and any other state that moved answers `DURABLE_TASK_STALE_STATE`. A daemon from this commit deploys before any runner from it, because an older daemon can still answer `reserved` and a newer runner cannot parse it.
- Stop of a fleet turn: same request and response. A run issued around the Stop is not issued, or is named in Stop's answer. An approval answered while a Stop of its turn is in flight waits for the Stop and answers as already resolved. A Stop and a resolution now wait behind any holder of the fleet's thread or of the fleet `FOR UPDATE` (activation, a setup save, an archive, a delete), and a wait past the login's lock bound answers the datastore error.
- Draft stream: state events arrive on a notice, or within 15 s after a lost one. The route description changes as §5 states. The bus message is `{"changed":"<draft id>"}` on the draft's item subject.
- Runner config: `supervisor.renewal_interval_ms` is refused at boot. The runner renews on the heartbeat interval the daemon advertises.
- Daemon config: the default `[runner.run] ttl_seconds` is 38, and a value under `heartbeat_interval_seconds` + 28 is refused at boot. `[runner.health] heartbeat_interval_seconds` is refused above the least of 24, `ttl_seconds` − 28 and (`ttl_seconds` − 1) / 3; today it is valid up to 52 at the default offline threshold. The daemon and its `ttl_seconds` of 38 deploy before any runner from this commit, and a daemon rolled back under 38 takes its runners back first: a runner on a 10 s round against a 35 s run expiry has no slack left after one lost round.
- Runner stream protocol: unchanged. The runner sends no ping frame; the daemon still answers one.

## Invariants

1. One call per run and operation — `uq_decision_calls_operation` is the issue statement's conflict target; it assumes one Postgres primary. Shortest counterexample: Dimension 2.2.
2. No call is issued when the thread, run, named task or source turn changed in a transaction that committed before the issue statement locked that row — the issue statement's `FOR SHARE` steps and their predicates. Rows the issue statement only joins are outside it (exposure 2). Counterexamples: Dimensions 2.6 and 2.7.
3. A call is issued with its payload — one statement inserts both; a payload erased later is `decision/replay.rs`'s to answer. Counterexample: Dimension 2.4's counts.
4. No run is issued for a turn settled before the issue read it — the issue's `FOR SHARE` read of the turn with both predicates. Counterexamples: Dimensions 3.1 and 3.2.
5. The runner's only interval loop is the activity flush — the ast-grep rule of Dimension 6.10, run by `make lint-all`. That the heartbeat keeps no cadence sleep of its own is Dimension 6.2's to prove.
6. The round period fits every allowed run expiry, and the heartbeat fits the idle timeout — the six compile-time asserts §6 lists and the garde ranges on `ttl_seconds` and `heartbeat_interval_seconds`; a value out of order fails the build or the boot.
