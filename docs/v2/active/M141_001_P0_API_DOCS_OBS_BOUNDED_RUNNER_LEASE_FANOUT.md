## Overview

**Goal (testable):** A lease poll that finds no work performs zero Postgres round-trips and one bounded Redis read, so idle control-plane cost scales with runner count alone and never with the number of active fleets.

**Problem:** Enrolling runners degrades the control plane even when every runner is idle. Operators see Postgres connection pressure and lease latency climb as the platform adds fleets, with no user traffic to explain it. Adding execution capacity — the one thing a runner is for — makes the API slower for everyone, so the fleet cannot grow.

**Solution summary:** Every idle lease poll currently walks the entire active-fleet population to discover that nothing is queued. `assign.listCandidates` returns all active fleets with no bound, and `selectInner` iterates the whole list, spending a Postgres claim per candidate and up to three Redis commands on each candidate it wins. Ingress already funnels through one producer, so the fix is to record which fleets actually hold work at the moment they receive it, and let the lease consult that index first. An empty index answers no-work immediately; a non-empty one bounds the Postgres candidate query to a named ceiling. A low-cadence sweep re-derives readiness from the streams themselves, so a lost index entry self-heals instead of stranding an event. The `/v1/runners` wire protocol, the per-fleet claim, and the fencing semantics are untouched.

## Sections (implementation slices)

### §1 — Ingress records which fleets hold work

A fleet's stream receives an event through exactly one producer. Recording readiness there makes the index correct for all five ingress paths without touching any handler. The mark happens only after the append succeeds, so a failed append never leaves a false-ready fleet. The write is best-effort and never fails the ingress call: a fleet whose readiness write is lost still has its event in the stream, and §3 recovers it. **Implementation default:** one Redis **hash** keyed per the constant in `queue/constants.zig` — field is the fleet id, value is that fleet's generation token. A set cannot carry a token per member, and encoding the token into the member would break both fleet-level deduplication and direct removal, so the hash is load-bearing rather than a preference: it keeps O(1) marking and field-level dedup while giving §3's compare-and-clear something to compare. **The token is a freshly minted Universally Unique Identifier version 7 (UUIDv7), drawn per mark from the existing `types/id_format.zig` minter** — not a caller-supplied value, not a per-fleet counter, and not a shared Redis sequence. `clear` asks one question only: *is the stored token still the one this poll observed?* That is an equality test, never an ordering test, so nothing in the design needs tokens to be comparable — which is what makes a minted identifier the right shape and a counter the wrong one.

Every counter-shaped alternative fails on **reuse**, and each fails at a different layer. A caller-supplied token (a stream entry id included) can land out of order when two appends for one fleet race, regressing to a value a poll already observed. A per-fleet counter fails the other way: `clear` deletes the field, so the next mark restarts that fleet's count and re-mints a token a stale poll still holds — and since every successful drain deletes the field, that reuse is the normal cycle, not a rare eviction. Hoisting the counter into one shared Redis sequence closes both, but the sequence key is itself non-durable: an eviction, flush, or lossy failover restarts it low and re-issues live tokens, so it needs a clock-derived seed scaled by a per-tick headroom multiplier — and even then a reset combined with a backwards clock reuses. In every case a stale compare-and-clear matches and erases the mark for genuinely new work.

A minted UUIDv7 has no such layer. Its 74 bits of entropy carry uniqueness outright, so there is no counter to reset, no second key to lose, and **no dependence on the clock for correctness**. Its leading 48-bit big-endian millisecond field does make tokens sort chronologically, which is a pure debugging benefit: an operator reading the index sees the order marks were issued. A slipped clock degrades that readability and nothing else — it cannot cause reuse, because uniqueness never rested on the timestamp. Reuse would require a 74-bit collision landing on the same fleet's field against a token a live poll is holding; that is not a failure mode the design has to answer for, and were it ever to occur it degrades to one lost mark, which §3's sweeper probe recovers. Minting is also allocation-free (`generateUuidV7` returns the 36-byte text by value) and reuses the one identifier spelling the rest of the system already compares, so ingress pays a stack buffer rather than a Redis round-trip: `mark` is a single `HSET`, not a script. This choice also sidesteps stream ids being `<ms>-<seq>` strings whose lexicographic order is not their real order (`100-0` sorts before `99-0`), which a natural string comparison gets silently wrong.

- **Dimension 1.1** — an accepted fleet event marks its fleet ready before the producer returns, for every ingress path → Test `test_fleet_event_marks_fleet_ready`
- **Dimension 1.2** — a readiness write failure logs, increments a counter, and still returns the entry Identifier (ID) to the caller → Test `test_ready_mark_failure_never_fails_ingress`
- **Dimension 1.3** — a token is never reused: N racing marks for one fleet each leave a distinct canonical UUIDv7, and a fleet cleared and then re-marked receives a token unequal to the one it held before — the case every counter shape gets wrong, since a deleted field restarts its count. Marking needs no second Redis key, so there is no sequence to evict, reset, or seed. Tokens minted in ascending wall-clock order also sort ascending, the readability property an operator relies on when reading the index → Test `test_tokens_never_repeat`

### §2 — An idle poll stops touching Postgres

The lease consults readiness before it opens a Postgres connection. An empty index answers no-work with the existing backoff hint and zero database work — the dominant steady state on any deployment with more fleets than concurrent events. A non-empty index yields a bounded slice of fleet ids, and only those ids enter the candidate query. The label gate and sticky ordering are properties of the candidate query and stay exactly where they are: the query keeps `required_tags <@ labels` and the sticky-first ordering, and gains a membership restriction plus a ceiling. Readiness narrows the input; it never decides eligibility. **Implementation default:** the candidate ceiling is a named constant in `src/lib/common/constants.zig` alongside `NO_WORK_RETRY_AFTER_MS`, because it trades the same axis — per-poll cost against discovery latency — and operators tuning one must see the other.

- **Dimension 2.1** — a poll against an empty readiness index acquires no pool connection and issues no query → Test `test_idle_poll_performs_zero_pg_roundtrips`
- **Dimension 2.2** — a non-empty readiness index restricts the candidate query to its fields and never returns more rows than the ceiling → Test `test_candidate_scan_is_bounded_by_ceiling`
- **Dimension 2.3** — a ready fleet whose `required_tags` exceed the runner's labels is not leased to that runner → Test `test_ready_index_never_bypasses_label_gate`
- **Dimension 2.4** — the runner's own affinity still sorts ahead of other ready candidates → Test `test_sticky_ordering_survives_ready_filter`

### §3 — Readiness never strands an event

The index is a hint, not the system of record; the streams are. Two mechanisms keep a hint failure from becoming lost work. **The clear site is where the code already proves emptiness.** Do not test whether the stream is empty — it never is. Ingress trims at `MAXLEN ~ 10000`, so delivered entries persist, and a stream-empty condition would essentially never fire, leaving every fleet that ever received an event permanently in the index and restoring the very scan this spec removes. The real proof already exists: in `acquireFresh`, a claim-won poll whose own-PEL read and whose undelivered read both return null has established there is nothing deliverable, and that site already releases the claim. Clear readiness there, at zero additional Redis cost. **But the clear must be compare-and-clear, never an unconditional delete.** The per-fleet affinity claim serializes runners against each other, but ingress takes no claim — it can append and mark at any instant, including between the two null reads and the clear. An unconditional delete would then erase a mark for a genuinely undelivered event, and the sweeper would not rediscover it until its next pass: a routine multi-second pickup delay on a completely healthy system, replacing today's sub-second idle poll. That is a latency regression this spec must not introduce, so each index entry carries a generation token that every mark advances by atomic increment, `peek` returns each fleet's token alongside its id, and `clear` deletes only if the stored token still matches, evaluated atomically inside Redis rather than read-then-delete from the caller. This is why §1's backing store is a hash: a set has nowhere to put that token. The increment must be the store's own atomic operation rather than a value the caller computes and writes — a caller-supplied generation can be written out of order by concurrent marks and regress, which reopens the race it was added to close.

**The backstop is the sweeper that already runs.** `reclaim_sweeper` already wakes on `fleet_reclaim_interval_ms`, pulls active fleets from Postgres, and walks each fleet with a registered lifecycle in `serve_background` and an integration test that drives `sweepOnce` directly. Readiness re-marking belongs inside that existing loop, not in a second thread. It closes the hole the clear site leaves: the own-PEL read sees only this instance's pending entries, and a reclaimed stray re-enters the lease flow only "on the next poll" — which never comes once readiness is cleared. **It must probe for undelivered entries, not only for pending ones.** Today `reclaimFleetStrays` calls only `XAUTOCLAIM`, which reads the pending list. The worst case this spec must survive is a successful stream append whose readiness mark then fails: that entry is undelivered and in nobody's pending list, so `XAUTOCLAIM` can never see it and no amount of re-marking-on-reclaim recovers it. The fleet becomes permanently invisible and its event is stranded forever — the exact failure this section claims to prevent. The sweeper therefore needs a bounded per-fleet undelivered probe and must re-mark on a positive result, independent of whether anything was reclaimed. **Implementation default:** the probe compares the group's `last-delivered-id` against the stream's `last-generated-id`, NOT the group's `lag` field. `lag` is deliberately nil whenever entries have been deleted or trimmed — and ingress trims at `MAXLEN ~ 10000`, so a production stream reaches that state as a matter of course and a lag-based probe would silently stop answering. The comparison must parse both `<ms>-<seq>` identifiers numerically; string comparison gets it wrong for the same reason named in §1 (`100-0` sorts before `99-0`), so the comparator is a pure function with its own unit test. The sweeper additionally re-marks on a non-empty PEL (one `XPENDING` summary), which closes the cross-replica strand in one sweep interval instead of waiting out the auto-claim min-idle. **The sweeper re-marks but never clears** — a false-positive entry costs one wasted candidate check, a false-negative strands an event.

**The recovery bound scales with fleet count, and the architecture must publish it as such.** The sweep reaches at most `SWEEP_BATCH_LIMIT` active fleets per pass, so worst-case recovery for a strand outside the current batch is `fleet_xautoclaim_min_idle_ms_int + ceil(active_fleets / SWEEP_BATCH_LIMIT) × fleet_reclaim_interval_ms` — not a flat "min-idle plus one interval", which is only the single-batch case. That formula is the operator-visible promise; stating the flat figure would understate recovery by the same factor this spec is removing from idle cost. **The batch bound stays as shipped (Indy's call — see Discovery).** Raising it, or adding a boot-time reconciliation pass over every active fleet, both buy a shorter cold-start window at the cost of scaffolding the future scheduler replaces; the keyset cursor below is retained because without it the fleets past the first batch are not merely slow to reach but never reached at all.

- **Dimension 3.1** — a claim-won poll clears readiness exactly when both the own-PEL read and the undelivered read return null, and never merely because the stream holds delivered entries → Test `test_ready_cleared_only_when_nothing_deliverable`
- **Dimension 3.6** — an ingress mark landing between the two null reads and the clear survives: the token has advanced, the clear is a no-op, and the next poll leases the new event without waiting for a sweep → Test `test_clear_does_not_erase_racing_ingress_mark`
- **Dimension 3.2** — a fleet with a pending PEL entry stays ready and is re-delivered → Test `test_pending_entry_keeps_fleet_ready`
- **Dimension 3.3** — an event appended to the stream whose readiness mark then failed is found by the sweeper's undelivered probe and re-marked, with nothing in any pending list → Test `test_sweeper_recovers_undelivered_without_pel_entry`
- **Dimension 3.4** — a stray reclaimed by the sweeper re-marks its fleet ready, so a strand left by another replica becomes leasable without waiting for unrelated ingress → Test `test_reclaimed_stray_remarks_readiness`
- **Dimension 3.5** — the sweeper's active-fleet scan advances across passes rather than repeating one head of the list, so every active fleet is reached above the batch bound → Test `test_sweeper_scan_advances_across_passes`
- **Dimension 3.7** — a fleet that leaves `active` (deleted, stopped, killed, paused) loses its readiness field at the lifecycle site, because the poll-site clear is reachable only for fleets the candidate query returns and that query filters `status = 'active'`. Without this the field is unremovable and permanently holds one slot of the bounded peek sample. The clear here is unconditional rather than token-guarded — that guard protects live work, and an unleasable fleet has none — and it runs only after the Postgres write commits, so a rolled-back transition cannot erase a live mark. ### §4 — Consumer-group creation stops costing a Redis command per candidate

`ensureFleetConsumerGroup` issues an `XGROUP CREATE` on every call and relies on the `BUSYGROUP` error for the steady state, so it costs one Redis round-trip per candidate per poll forever. The group is durable, so the result is memoizable in-process. Memoization is per-process and bounded; a cold process, an evicted entry, or a genuinely new fleet still takes the real path. **Implementation default:** mirror the fixed-capacity, allocator-free table already used by `metrics_runner.zig`, because the same constraints apply — a bounded key space, no allocator on a hot path, and a defined overflow behaviour.

- **Dimension 4.1** — repeated leases against one fleet issue the group-create command once per process → Test `test_consumer_group_ensured_once_per_process`
- **Dimension 4.2** — a fleet beyond the memo capacity still gets a correctly created group → Test `test_group_memo_overflow_still_creates`
- **Dimension 4.3** — a group deleted out-of-band invalidates its memo entry on the resulting error and is recreated on the next poll, rather than failing that fleet until process restart → Test `test_group_memo_invalidates_on_missing_group`

### §5 — Poll cost is visible on the existing scrape path

The defect this spec fixes was invisible: nothing on `/metrics` distinguished an idle poll that cost one Redis read from one that walked every fleet on the platform. The new families make per-poll cost and readiness depth observable so a regression is caught by a dashboard rather than by a Postgres incident. They carry no fleet, workspace, tenant, or runner label, so they live with the other global unlabelled families rather than in the per-runner table. **Readiness depth is sampled, not counted.** The index is one hash shared by every replica, so a process-local counter incremented on mark and decremented on clear cannot describe it: one replica marks while another clears, a restart zeroes the local delta, and a repeat mark for an already-present fleet overwrites a field without changing the count. The gauge would drift permanently from what it claims to measure and mislead exactly the dashboards this section adds. It is therefore **sampled** — the reclaim sweeper reads the hash's field count once per pass into memory and `/metrics` renders that, keeping the render path datastore-free as `runner_fleet.md` requires at the cost of one sweep interval of staleness, which a slow-moving gauge tolerates. Every replica samples the same shared hash, so the fleet-wide value is any single instance's series and the dashboard must not sum them. Names, units, and attribute keys come from the pinned semantic registry created by M139_004; this section adds no private descriptor of its own.

- **Dimension 5.1** — candidate-scan depth and per-poll database round-trips render as bounded, unlabelled families → Test `test_poll_cost_metrics_render_unlabelled`
- **Dimension 5.2** — readiness depth renders the sweeper's sample of the shared hash, not a process-local delta: marks applied by a second client are reflected after a sweep, and a simulated restart does not corrupt the value → Test `test_ready_depth_samples_shared_index`
- **Dimension 5.3** — readiness write failures render and move with observed state → Test `test_ready_failures_observable`

### §6 — Authenticating a poll stops costing a Postgres read

Every `/v1/runners/me/*` call resolves `sha256(agt_r)` against `fleet.runners` before the handler runs, so even with §2's zero-Postgres candidate path an idle runner still costs one database read per heartbeat and per lease poll — a cost that scales with runner count times poll rate and buys the same answer every time. The verdict is memoized in-process: a mutex-guarded table of `token_hash → {runner_id, active}` rows consulted by the existing `LookupFn` host (`cmd/serve_runner_lookup.zig`), leaving `src/auth/**` portability-locked and the middleware untouched. (§7 later replaces the bespoke direct-mapped storage with the shared `common.CacheTable`; every policy described below is unchanged by that move.)

**The expiry is the correctness bound, and it is pinned to the heartbeat.** The machine that serves an operator's cordon/drain/revoke drops the entry itself after the write commits, so on today's single-machine deployment a state change bites on the very next request. When the control plane runs 2–3 machines, the operator's request lands on one; the others keep answering from memory until their entry expires — so `ENTRY_TTL_MS = HEARTBEAT_INTERVAL_MS`, and a runner taken out of service is refused everywhere within one liveness cycle. Misses are deliberately not memoized: nothing is gained (a token minted later was never asked about), and a miss memo would hand an unauthenticated caller a way to evict live runners from the table by presenting garbage.

This is the deliberately short-lived shape, chosen over the two designs that keep entries exact across machines (a `PUBLISH`-and-subscriber invalidation, or a shared Redis stamp checked per poll): the first adds the second background-thread pattern this spec's Product Clarity §6 excludes plus a reconnect miss-window needing its own backstop, the second adds a Redis read per poll. Both are scaffolding for a decision not yet made — whether runner credentials stay opaque at all (a self-proving token needs no lookup and no cache; see Discovery). If that lands, this table is deleted, not extended.

- **Dimension 6.1** — a memoized verdict answers without a database read, and stops answering the instant its heartbeat-pinned window closes → Test `runner_token_cache_test` (hit, expiry boundary, expired-row drop)
- **Dimension 6.2** — a cordon, drain, revoke, or delete drops the runner's entry on the machine that served it, after the write commits → Test `runner_token_cache_test` (invalidation), call sites in `runner_patch.zig`/`runner_delete.zig`/`liveness_sweeper.zig`. **Every writer of `admin_state` carries this obligation, not only the request handlers**: `liveness_sweeper.markDrainedIfIdle` flips `draining → drained` on a background thread, and without invalidating there it left the drained runner authenticating from memory on the very machine that demoted it.
- **Dimension 6.3** — a recycled or colliding slot never answers with a different runner's identity, an oversized id is skipped rather than truncated, and unknown tokens are never memoized → Test `runner_token_cache_test` (recycling, width, refusal cases)

### §7 — The two hand-rolled tables become one shared primitive

§4 and §6 each added a fixed-size in-process table, written independently, and both landed on the same shape: a direct-mapped array of 4096 slots keyed by a hash. Direct-mapped means no probing, so two live keys landing on one slot evict each other on every interleaved access and both fall back to the real lookup permanently — the table is worst at exactly the scale it exists for, and widening it only makes that rarer rather than survivable. §6 already paid for this once: pre-landing review found 128 slots put ~30 of ~100 runners in a shared slot, and the fix was to widen to 4096.

`common.CacheTable` replaces both with an N-way set-associative table: each bucket holds `bucket_size` entries with least-recently-used eviction *within* the bucket, so colliding keys coexist and only the coldest leaves. Fixed capacity, no allocator, no deinit, per-entry expiry. It is deliberately **unsynchronized** — a consumer picks a lock matched to its own correctness needs instead of every consumer paying for the strictest one — and `peek` is a provably non-mutating reader, which is what lets a caller hold only a shared lock.

Placement is forced rather than chosen. `src/build/auth_tests.zig` links only `src/agentsfleetd/auth/**` plus a fixed list of named modules, so a domain-local helper under `src/agentsfleetd/` would fail `test-auth` the moment `runner_token_cache.zig` imported it. `src/lib/common/` reached through the named `common` module is the one legal home, and it keeps the file std-only and liftable into a package.

Adapted from **ghostty** `src/datastruct/cache_table.zig` (MIT) — the bucket-and-lengths layout, in-bucket LRU by rotation, the optional eviction hook. Its `fastmem.rotateIn` is deliberately not taken: it pulls `extern "c" memmove` declarations, and `common` sits on the auth portability gate's allow-list. The bucket index for a digest key comes from **bun** `src/runtime/api/bun/SSLContextCache.zig` (MIT) — a SHA-256 is already uniform, so re-hashing it buys nothing. Per-entry expiry, expired-slot reuse, `peek`, and `removeMatching` exist in neither upstream.

- **Dimension 7.1** — colliding keys coexist to bucket depth, an expired entry is reused before any live entry is evicted, and a churn far exceeding capacity never returns one key's value for another → Test `cache_table_test`
- **Dimension 7.2** — `runner_token_cache` keeps every auth-specific policy across the move: constant-time comparison, misses never memoized, the invalidation generation guard, invalidation by runner id → Test `runner_token_cache_test`, **unchanged**, which is the evidence the behaviour is
- **Dimension 7.3** — `fleet_group_memo` stores the fleet id and compares it in full, retiring the hash-collision case its own module comment admitted could report a fleet ensured when it is not; `isEnsured` holds the lock shared so publish-path readers do not serialize → Test `fleet_group_memo_test`

## Failure Modes

| Mode | Cause | Handling (system response + what the caller observes) |
|------|-------|--------------------------------------------------------|
| Readiness mark lost | Redis unavailable at ingress, or a later eviction, failover, or out-of-band delete | Log, increment the failure counter, return the entry ID normally. The sweeper's undelivered probe re-marks the fleet on a later pass — this is the case `XAUTOCLAIM` alone cannot see, so the probe is mandatory, not an optimization. The event is never lost. |
| Readiness peek fails, or the pool is exhausted | Redis unavailable at lease time, or unrelated Postgres saturation during a busy poll | Treat as retryable, never fatal; log and answer no-work with the existing backoff hint. Runners retry, and no partial or unbounded Postgres scan is attempted as a fallback. The pool-exhaustion half is unchanged existing behaviour. |
| Fleet stuck ready, or two runners peek the same fleet | Every ready fleet requires tags no polling runner advertises; or concurrent polls read overlapping slices | A tag-mismatched fleet is genuinely non-empty so readiness is not cleared, and the ceiling plus randomized sampling stops it starving the rest. Overlapping slices are unchanged: `affinity.claim` picks exactly one winner and the loser moves on having read no event. |
| Readiness cleared with work pending | Ingress appends and marks between the two null reads and the clear; ingress holds no claim, so nothing serializes it against the poll | The token-guarded compare-and-clear sees a different token and becomes a no-op, leaving the new mark intact so the next poll leases it. Falling back to the sweeper here would be a multi-second pickup delay on a healthy system, not an acceptable degradation. A sweeper re-mark landing mid-drain is the same shape and equally safe. Concurrent marks and delete-then-recreate are covered by the same property: each mark mints a fresh UUIDv7, so no interleaving and no cleared-then-recreated field can reproduce a token a poll observed. There is no counter and no second key, so no eviction, flush, failover, or clock anomaly can re-issue a live token — the residual the counter shapes carried does not exist here. |
| Memo returns a stale hit | Consumer group deleted out-of-band | The read path surfaces it as retryable, invalidates the entry, and the next poll recreates the group. |
| Readiness field orphaned for a fleet that is gone or no longer `active` | The lifecycle clear (§3, Dimension 3.7) covers the API paths. Residual: an out-of-band delete (direct SQL, a cascade), or a `forceClear` whose Redis write failed | The orphan holds one slot of the bounded peek sample and nothing removes it. **Bounded, observable, and recoverable rather than fixed in code:** below 64 entries `HRANDFIELD` returns every field, so orphans cost nothing at all; above it a live fleet is sampled with probability `ceiling/N`, adding ≈ `N / (ceiling × runners)` seconds of pickup latency and never an error, because the streams stay the system of record. The readiness-depth gauge (§5) climbs monotonically long before latency moves, and recovery is `DEL` on the index — the sweeper re-marks every active fleet holding undelivered work within `ceil(active_fleets / SWEEP_BATCH_LIMIT)` intervals — or a surgical `HDEL` of index fields that are not active fleet ids. Making the residual self-healing wants a durable tombstone the pruner can retry against, since a failed `forceClear` leaves nothing to retry from; that is scheduler scope, not M141. |

## Invariants

1. A poll whose readiness peek returns empty performs zero Postgres pool acquisitions — enforced by a test asserting the acquire count, not by review.
2. The candidate query returns at most the named ceiling of rows — enforced by the query's own bound, asserted in test.
3. Readiness is cleared only from the `acquireFresh` site where both reads returned null, and only by a token-guarded compare-and-clear evaluated atomically in Redis — enforced by `clear` taking the observed token as a required argument, so an unconditional delete is not expressible, and asserted by a racing-ingress test.
4. Every fleet holding an undelivered entry or a non-empty PEL is either in the readiness index or re-marked by the reclaim sweeper — enforced by the sweeper test that deletes an entry and asserts recovery, and by the reclaim test that asserts a reclaimed stray re-marks its fleet.
5. The `/v1/runners` wire protocol is byte-identical — enforced by the frozen protocol tests in `src/lib/contract/`, which this spec does not modify.
6. Every candidate still passes `required_tags <@ labels` — enforced by keeping the gate in the query and asserting a tag-mismatched ready fleet is never leased.
7. No new metric carries a fleet, workspace, tenant, event, lease, or runner label — enforced by the unlabelled-render test.
8. A readiness failure never fails an ingress call or a lease reply — enforced by the ingress and peek failure-injection tests.
9. The `/metrics` render path issues no Redis and no Postgres call, and readiness depth is the sweeper's sample of the shared hash rather than a process-local delta — enforced by `metrics_counters` exposing only a setter for the sampled value, with no mark/clear increment path, plus a render test that runs with the datastore unavailable.
10. A runner taken out of service can authenticate nowhere later than one heartbeat interval after the operator's write commits — enforced by the exclusive expiry-boundary test, the `ENTRY_TTL_MS == HEARTBEAT_INTERVAL_MS` pin test, and the invalidation calls at both operator-plane write sites.
11. The token memo stores the token's hash and never the token, answers only for full-width hashes, and never memoizes a miss — enforced by the width-refusal tests and by `lookup` memoizing only after a row was read.

## Product Clarity (authoring record)

1. **Successful user moment** — an operator triples the runner count to absorb a busy week, watches the `agentsfleetd` dashboard, and sees database load flat. The control plane did not notice.
2. **Preserved user behaviour** — every runner already enrolled keeps working with no re-registration, no version pin, and no configuration change; pickup latency for a busy fleet is unchanged; the frozen `/v1/runners` protocol means an unmodified runner binary talks to an upgraded control plane.
3. **Optimal-way check** — the direct path is to stop asking a question whose answer is already known at ingress. The unconstrained-optimal shape pushes work to runners and drops polling entirely; that touches the frozen protocol and the enrolled-runner population, so it stays a later lever. Readiness gets the same idle-cost win without either cost.
4. **Rebuild-vs-iterate** — iterate. The claim, fencing, reclaim, and label-placement semantics are correct and load-bearing; only candidate discovery is wrong. A rebuild would risk run-to-run determinism the current design already guarantees.
5. **What we build** — a readiness index written at the single ingress producer, a ready-first bounded candidate path in the lease, a self-heal sweep, a memoized consumer-group ensure, and poll-cost metrics on the existing scrape path.
6. **What we do NOT build** — no push delivery, no protocol change, no scheduler, no schema change, no runner-side telemetry, no second background-thread pattern.
7. **Fit with existing features** — compounds label placement (M85_001) and reassignment (M84_002) by making their candidate set cheap to evaluate. The one thing it must not destabilize is the per-fleet claim and fencing guarantee that keeps two runners off one fleet.
8. **Surface order** — N/A — no user surface; this is control-plane internals with an operator-metrics surface only.
9. **Dashboard restraint** — the new panels show only counters that exist; no readiness health claim ships before the sweep-recovery counter is live to back it.
10. **Confused-user next step** — an operator seeing lease latency checks the scan-depth and readiness-depth families on `/metrics`, which distinguish "many fleets hold work" from "discovery is scanning too far"; the corrected `scaling.md` sizing procedure names the knob for each.

## Decomposition & alternatives (patch vs refactor)

- **Chosen shape:** one workstream owns ingress marking, lease consumption, the sweep, and the metrics because they are one mechanism — shipping the index without the sweep would trade a cost defect for a correctness defect, and shipping either without metrics would leave the regression as invisible as the original.
- **Alternatives considered:** a bare `LIMIT` on the existing scan was rejected because it caps discovery throughput without removing the per-poll Postgres cost, and silently starves fleets past the bound. Sharding fleets across runners was rejected because it converts sticky preference into ownership and breaks the rebalance-free enrolment property. Push or long-poll delivery was rejected for now because it changes the frozen protocol and every enrolled runner, which is a larger upfront decision than this defect warrants. **Patch-vs-refactor verdict:** this is a **refactor** of candidate discovery — the code that decides which fleets a poll examines is replaced — while the claim, fencing, billing, and delivery paths it feeds are untouched.

The index would have grown to hold every fleet and silently restored the O(fleets) scan. Now clears at the `acquireFresh` site where both reads already returned null; §3, Invariant 3, and Dimension 3.1 rewritten to guard the regression.

- **Greptile review on PR #548 — eight P1s across six rounds, all accepted.** Each round exposed that the previous fix was incomplete one layer down, which is the useful record here: the readiness index needed a correct *concurrency model*, not a correct *clear*. **R1(a)** the clear raced ingress — ingress takes no affinity claim, so an append-plus-mark between the two null reads and the clear would be erased by an unconditional delete, pushing pickup out to a sweep pass on a healthy system; `clear` became token-guarded (Dimension 3.6). **R1(b)** readiness depth as a process-local mark/clear counter cannot describe a store shared by every replica — cross-replica mark/clear and restarts drift it; now sampled by the sweeper and rendered from memory, keeping the scrape path datastore-free (Dimension 5.2, proven by marking from a second client, and documented as not summable across replicas). **R2** the token-guarded clear was specified against a Redis *set*, which has no per-member value to hold a token, while `peek` still returned bare ids — the comparison was unimplementable as written; backing store became a hash and `peek` yields `[]Ready` pairs. **R3** the token was then the stream entry id, but concurrent appends complete their marks in either order, so a caller-supplied generation can land out of order and regress, reopening the race it closed; the token became a counter the store increments atomically. **R4** that counter was per-field, and since `clear` deletes the field, the next mark restarted the count and re-minted a token a stale poll still held — an ABA reuse that every drain-then-refill cycle reproduces, not a rare eviction; the token moved to one shared sequence. **R5** that sequence key is itself non-durable, so an eviction, flush, or lossy failover restarts it low and re-issues live tokens — the same reuse one level up; creating an absent sequence now seeds from a clock-derived floor. **R6** a bare timestamp floor is still insufficient — many marks fit inside one clock tick, so the counter overruns the next tick's floor and a reset re-issues that span with no clock anomaly at all; the seed is now scaled by a per-tick headroom multiplier sized well beyond any plausible ingress rate. Stated in §1 as mitigation rather than proof: a non-durable store cannot give absolute uniqueness, and the true residual (reset plus a backwards clock) degrades to a lost mark that the sweeper probe recovers — acceptable only because the datastore has already failed, unlike the healthy-system races in R1–R4. **R4–R6 were all one question — where token identity comes from — and each fix was correct at its layer with a hole beneath it.** *(Superseded at PLAN — see the PLAN-stage review entry above. The ladder was resolved rather than extended: R3–R6 are all fixes to an ordering problem, and `clear` never orders tokens, it only compares them for equality. The token is now a minted UUIDv7, which carries uniqueness in its entropy, needs no stored counter or second key, and leaves no reset/eviction/clock residual for a later round to find. This archived record stands as the reasoning that led there; the R5/R6 clock-seed mitigation it lands on is no longer what ships.)*
